# 📊 [Catalog Service] AS-IS 아키텍처 성능 병목 리포트 (1차 부하테스트)

본 문서는 현재 카탈로그 시스템(AS-IS) 아키텍처가 대규모 트래픽을 맞이했을 때 발생하는 **읽기(Read) 병목 현상**을 수치로 증명한 1차 성능 테스트 리포트입니다.

---

## 1. 카탈로그 읽기(Read) 성능 한계 증명

> **테스트 목적:** 캐시(Redis)가 적용되지 않은 상태에서 대량의 Read 트래픽이 디스크 기반 DB(MongoDB)로 직접 향할 때 발생하는 I/O 지연 증명

### 📌 더미 데이터 세팅 및 JMeter 타격 결과

- **환경:** MongoDB 내 `p_product_views` 10만 건 더미 데이터 세팅 완료 (`PerfDataInitializer` 사용)
- **요청 타겟:** `GET /api/v1/products` (카탈로그 메인 API)
- **부하 규모:** 100 Threads, Loop 10 (총 1,000건 요청, 1 Ramp-up 스파이크 테스트)
- **결과 요약:**
    - **평균 지연 시간(Average):** `539ms` (약 0.5초)
    - **최대 지연 시간(Max):** `2,153ms` (약 2.1초)
    - **에러율(Error %):** `0.0%`
    - **처리량(Throughput):** `153.5 /sec` (목표치 200 TPS 미달)
- **분석:** 에러율은 0%로 안정적이나, 단순 메인 화면 조회 API임에도 매 요청마다 디스크(MongoDB)를 직접 조회하므로 심각한 **Disk I/O 병목**이 확인되었습니다.  
  트래픽이 몰렸을 때 평균 0.5초, 최대 2.1초의 응답 시간은 실제 예약 서비스 오픈 시 사용자 체감 속도(UX)를 심각하게 저해하고 대량 이탈을 초래할 수 있는 지표입니다. 또한 처리량 역시 디스크 I/O
  한계로 인해 목표치인 200 TPS를 넘기지 못했습니다.

## 💡 종합 결론 및 향후 작업방향 (TO-BE 기획)

1. **읽기 성능 단축:** 카탈로그 메인 조회 API에 **Redis 인메모리 캐시(Cache-Aside)**를 도입하여 Disk I/O 병목을 제거합니다.
2. **목표 수치:** 캐시 히트(Cache Hit)를 통해 기존 평균 500ms 대의 지연 시간을 **10ms 이하로 단축**하고, 처리량(Throughput)을 **200 TPS 이상**으로 끌어올리는 것을
   목표로 합니다.
3. **정합성 유지:** 상품 변경 시 Kafka 이벤트를 발행하여 실시간으로 캐시를 무효화(Invalidation)하는 로직을 추가 설계할 예정입니다.
